# Импорт снимков и история версий

[← Оглавление](project-docs.md)

## Команды

```bash
./getcsv.sh                                                        # sync: проверить портал, при обновлении скачать/импортировать/zip
.venv/bin/python -m checkph.sync                                   # то же без обёртки
.venv/bin/python -m checkph.sync --force                           # скачать даже при совпадении курсора
.venv/bin/python -m checkph.sync --compress-existing               # упаковать старые каталоги YYYYMMDD в zip

.venv/bin/python -m checkph.importer --backfill                    # все inCSV/archive/YYYYMMDD(.zip) по порядку
.venv/bin/python -m checkph.importer --dir inCSV/archive/20261004.zip
.venv/bin/python -m checkph.importer --dir /path --date 2026-10-04 # дата явно
.venv/bin/python -m checkph.importer --backfill --db other.db --archive /path/to/archive
```

`--backfill` перебирает каталоги `YYYYMMDD` и файлы `YYYYMMDD.zip` / `YYYYMMDD-HHMM.zip` по возрастанию имени, дату берёт из имени (`YYYYMMDD-HHMM` → `YYYY-MM-DDTHH:MM`), уже импортированные даты пропускает. Прочие имена игнорируются. По каждому снимку в лог выводится сводка: сколько версий открыто, закрыто, без изменений, сколько операторов новых и переименовано.

## Периодическая синхронизация (`checkph.sync`)

Отдельный процесс от бота. Планировщик — `deploy/checkph-sync.timer` (каждые 6 часов в :15) или cron `15 */6 * * *`.

Алгоритм одного запуска:

1. `flock` на `inCSV/archive/.sync.lock`.
2. Упаковать оставшиеся каталоги `YYYYMMDD/` в zip (если есть).
3. Скачать индекс `/downloads/`. Если даты четырёх CSV совпадают с `sync_state` и последняя проверка содержимого моложе 7 дней — выход.
4. Иначе скачать все четыре файла во `.incoming/` (один изменившийся файл со старыми тремя дал бы ложные закрытия). Если индекс сменился во время загрузки — повторить один раз.
5. `read_snapshot`. Ошибка — zip в `_rejected/`, курсор не сдвигать, код выхода 1.
6. Хеш равен последнему `import_batch.files_sha256` — обновить `sync_state`, архив не создавать.
7. Хеш новый — `source_date` из даты индекса; `import_snapshot`; упаковка в `archive/YYYYMMDD.zip`; копии в `inCSV/`; запись курсора.

Повторная публикация в тот же день с другим хешем: `YYYYMMDD-HHMM.zip`, `source_date` = `YYYY-MM-DDTHH:MM`.

## Алгоритм diff-импорта (`importer.import_snapshot`)

Одна транзакция на снимок (каталог или zip).

1. Если `import_batch` с такой `source_date` уже есть — выход без изменений (идемпотентность). Если дата не новее последней импортированной — ошибка: порядок импорта нарушен.
2. Снимок читается и валидируется `csv_reader.read_snapshot()` (см. [03-csv-format.md](03-csv-format.md)).
3. Создаётся `import_batch` с `sha256` CSV и числом диапазонов.
4. Операторы. Ключ — ИНН, при его отсутствии — имя. Для каждого ключа: самое частое написание в снимке становится `operator.name`; все написания попадают в `operator_name_variant` (`first_seen_batch` при первом появлении, `last_seen_batch` обновляется).
5. Диапазоны. Текущие открытые версии загружаются в словарь по ключу `(code, from_number, to_number)`, снимок сравнивается по значению `(operator_id, region_raw, gar_raw)`:

| Ситуация | Действие |
|---|---|
| есть в базе, нет в снимке | закрыть версию: `valid_to_batch = batch` |
| нет в базе | открыть версию: `valid_from_batch = batch` |
| есть, но значение отличается | закрыть старую, открыть новую |
| совпадает | ничего |

Смена написания имени оператора без смены ИНН версий диапазона не создаёт — она отражается только в `operator` и `operator_name_variant`. Это принципиально: в снимке 2024‑11‑11 реестр массово перевёл имена в верхний регистр (213 тыс. строк), и при хранении имени текстом это выглядело бы как 213 тыс. изменений.

## Снимки в архиве

| Архив | Дата в `import_batch` | Диапазонов | Открыто | Закрыто | Без изменений |
|---|---|---|---|---|---|
| `20240724.zip` | 2024‑07‑24 | 443 256 | 443 256 | 0 | 0 |
| `20240809.zip` | 2024‑08‑09 | 439 753 | 17 706 | 21 209 | 422 047 |
| `20240913.zip` | 2024‑09‑13 | 439 867 | 1 606 | 1 492 | 438 261 |
| `20241111.zip` | 2024‑11‑11 | 440 914 | 6 031 | 4 984 | 434 883 |
| `20261004.zip` | 2026‑10‑04 | 451 099 | 82 559 | 72 374 | 368 540 |

Оговорка про `20240724`: дата взята из имени каталога по решению владельца проекта. По содержимому этот снимок новее `20241111` — содержит написания операторов, появившиеся в реестре между сентябрём и ноябрём 2024, и больше диапазонов. Поэтому у части диапазонов история содержит переходы `2024‑07‑24 → 2024‑08‑09`, которые в реестре шли в обратную сторону. Если дата будет уточнена, порядок пересобирается заново: удалить `registry.db`, переименовать архив, выполнить `--backfill`.

## Пересборка

База целиком выводится из архива. Для пересборки достаточно удалить файл базы и выполнить `--backfill`; данные слоя 3 (наблюдения) при этом теряются — их нужно переносить отдельно, если они есть.

## systemd

```bash
# поправить WorkingDirectory и ExecStart в deploy/checkph-sync.service под свою машину
sudo cp deploy/checkph-sync.service deploy/checkph-sync.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now checkph-sync.timer
```
